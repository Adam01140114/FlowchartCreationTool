Form Quality Check
==================
Last updated: September 8, 2026

Ten rules a generated form must satisfy before it ships. A form can pass the
compiler's `auditForm()` — clean geometry, no unreachable nodes, no overlaps —
and still fail every one of these. The audit checks the chart. These check the
form.

Run 1 to 4 in order: rule 4 is the one that proves the first three, so it is
last. Rule 5 is structural and costs nothing, so check it whenever you like.


THE LAST STEP IS ALWAYS A HUMAN READ. IT IS NOT OPTIONAL.
---------------------------------------------------------

No packet ships on a green audit. The final step of every form or packet, after
every other rule passes, is to read the interview end to end, in order, as a
person meets it - and then answer it in the preview. Both halves, every time.

    node pipeline-review.js            # the whole interview, in reading order
    node pipeline-review.js --form DV-110
    node pipeline-review.js --section 5

WHY THIS IS A RULE AND NOT ADVICE

`pipeline-audit.js` only finds what someone taught it to look for. Every rule
in this document was written after a defect got through, which makes the audit a
regression test for mistakes already made - it can only prove a form is not
wrong in one of the ways something was wrong before. A packet reported zero
failures while asking

    "Do you have a dV 100[0].Page4[0].List6[0].Li7[0].item26d tf[0]?"

The rule against showing a person a field name had been enforced since the day
it was written. It looked for underscores, and the humanizer had already turned
"item26d_tf[0]" into "item26d tf[0]", so nothing matched.

One pass of pipeline-review.js over that same packet found four defects, none of
which broke a rule:

  - a raw AcroForm path asked as a question
  - items 6 and 7 of DV-100 - thirty-odd questions - with no gate in front of
    them, so a filer who said the abuse happened once was still asked about
    two more incidents
  - questions about the restrained person asking for "your date of birth"
  - an age asked as a currency amount

WHAT TO LOOK FOR

The audit cannot see any of these, because each needs a reader who knows what
the question means:

  - wording only a person holding the paper form could answer
  - the wrong subject: "your" about someone else, "they" about the filer
  - a run of questions with no gate in front of it
  - a control that does not suit the answer
  - two questions that read identically within one section
  - an option list that reads as a field name rather than a choice
  - anything a frightened person filling this in at 2am would stall on

THEN ANSWER IT

Reading the output is half. Open the preview, answer each gate No, and confirm
the block it guards actually disappears. Logic that is correct in the exported
JSON can still be overridden by how the form renders: a gated block chains
internally, and stacked mode used to judge each link on its own and show the
whole block anyway. The export looked right. The form was wrong.

================================================================================
RULE 1 — EVERY PDF FIELD IS REACHABLE FROM THE HTML FORM
================================================================================

Every fillable field on the PDF must be reachable from some field on the HTML
form, directly or indirectly.

  Directly    A question's nameId is the PDF field's name.
              `case_number` -> the field called `case_number`.

  Indirectly  The answer reaches the field through something else:
                - a hiddenLogic nodeId, where picking a dropdown option or
                  ticking a checkbox sets a hidden field named for the PDF box
                  (`serve_form_dv_110` = Yes  ->  `serve_form_dv_110_yes`)
                - a mirror, where one answer fills the same field on nine pages
                  (a case number repeated in every page header)
                - a packet mirror, where a value asked once in DV-100 also fills
                  DV-109 and DV-110

"Indirectly" is a legitimate route, not a loophole. What is NOT allowed is a
fillable field with no path back to anything the user is ever asked.

HOW TO CHECK

  1. List the sanitized PDF's field names:
       getForm().getFields().map(f => f.getName())
  2. List every name the generated form posts — question nameIds, option
     nameIds, and hiddenLogic nodeIds. Read them out of the exported GUI JSON,
     not out of the flowchart.
  3. Every PDF field name must appear in that list.

A field mapped to its own raw `id` in field_config (the escape hatch that stops
the sanitizer deleting it) is NOT reachable. It is preserved, not filled, and it
counts as a violation.

WHAT FAILURE LOOKS LIKE

Nothing. That is the problem. `/edit_pdf` returns 200 and hands back a PDF with
that box blank. No error is raised anywhere in the chain.

Do not confuse this rule with the mapping being *correct* — see Rule 4.


================================================================================
RULE 2 — ASK THE QUALIFYING QUESTION FIRST, NEVER FOLD IT INTO THE QUESTION
================================================================================

When the PDF says "If you have a car, list the make and model below", the form
asks two questions, in this order:

  1. "Do you have a car?"                        <- dropdown, Yes / No
  2. "What is the make and model of your car?"   <- only if Yes

It must NOT ask:

  "What is the make and model of your car, if you have one?"

WHY

A user without a car should never see the second question. Folding the condition
into the wording pushes the branching decision onto the user and leaves the field
blank-or-junk either way — and a blank the form never asked about is
indistinguishable from a blank the user chose.

THE TELL

Scan question text for a condition that has been smuggled into the wording:

    if you have        if any        if known        if applicable
    if it              if they       if there        (if ...)
    , if               , if it did not fit

Every one of those is a question that should have been two.

  node pipeline-audit.js

fails on them under rule 2. The rule listed these tells from the day it was
written and nothing enforced them, which is exactly how two survived a packet
that passed every other rule: "Your lawyer's information, if you have one" and
"Where does the restrained person live, if you know?". Both are a gate plus a
follow-up now - "Do you have a lawyer?" then the lawyer's details.

A gate with no PDF field is fine and expected. The form has no box for "do you
have a lawyer"; declare it with a gateQuestion and the compiler creates it:

    "conditional": { "onlyWhen": "has_lawyer",
                     "gateQuestion": "Do you have a lawyer?" }

TWO EXCEPTIONS, AND ONLY TWO

  - Continuation lines. "Continue your explanation, if it did not fit" is a
    second textarea for overflow from a single logical answer, not a separate
    fact. It is gated on the first line being filled, not on a Yes/No.

  - Genuinely optional detail inside an already-qualified block. Once the user
    has said they own an animal, "What is the animal's breed?" may be left blank
    without a gate — the qualifying question already ran. Word it plainly and
    let it be optional; do not append "if you know it".

A CONDITION IS NOT A GATE

A follow-up whose condition lists EVERY option of the question above it is not
gated at all - it shows whatever the filer answered. It reads like a gate in the
JSON, which is what makes it worth checking by machine rather than by eye:

  node pipeline-audit.js

reports them under rule 2. It is not a failure on its own, because listing every
option is also how the compiler rejoins a branch to the spine, and a question on
the spine genuinely should always show. What must not be in that list is a
follow-up the printed form qualifies - "Yes (If yes, describe gun or weapon)".

A GATE CAN BE RIGHT IN THE JSON AND STILL NOT HOLD

In section and all modes a question whose condition reads "Any Text", or which
lists every option of the one before it, is shown without waiting for an answer
- it comes next whatever you said. That judgement used to be made one link at a
time, so a gated block, which chains internally ("show when the date has any
text"), was declared unconditional question by question: answering "no" to the
gate hid the first question and left the other sixteen on screen. The rule is
transitive now - a question can only be always-visible if the question it waits
on is too - but the lesson is that the exported logic being correct proves
nothing on its own. Answer the gate in the preview and look.

A gate declared in the hints only binds if it names an option the interview has
already reached. Two things go wrong otherwise:

  - The gate names a question that comes LATER. hostFor() cannot nest under an
    option that does not exist yet, so it manufactures one, and you get a
    duplicate of the real question plus a gate reading "Do you want to answer
    this question?" - the vague gate this rule forbids. Fix the order, or leave
    the follow-up ungated; do not leave the invented gate.
  - The gate is declared on a repeating block or an exclusive group. Those are
    one question standing for a family of fields, so there is no member field
    whose conditional could carry it. Declare it on the block or group nameId
    in `questions`; the compiler reads it there.

WHERE THE GATE LIVES

The gate is a real question in the flowchart with its own nameId, and the
follow-up carries `logic.conditions` pointing at it. Do not invent a gate that
names a field which does not exist — the compiler will manufacture a question
for it, usually a near-duplicate of a real one. Check every `conditional.onlyWhen`
against the actual set of `newName`s.


================================================================================
RULE 3 — REPEATED ENTRIES USE A multipleDropdownType NODE
================================================================================

When the PDF gives room for several numbered entries of the same thing — three
cars, four animals, six firearms, three debts — do NOT emit one flat question per
slot:

  WRONG
    "What is the make and model of your first car?"
    "What is the make and model of your second car?"
    "What is the make and model of your third car?"

That asks every user about three cars. It assumes a count nobody gave, and the
user has to work out that questions 2 and 3 do not apply to them.

  RIGHT
    Ask how many, then collect that many entries:
      "How many cars do you have?"   ->  0 to 3
      then Make + Model per entry, repeated exactly that many times.

That is a single `multipleDropdownType` node. The two numbers on the node are the
minimum and maximum entry count; the field rows below are the fields collected
per entry.

THE SHAPE

  style      questionType=multipleDropdownType  (on a nodeType=question cell)
  _questionText   the "how many" question
  _twoNumbers     { "first": <min>, "second": <max> }
  _textboxes      one entry per field collected per repetition, each with a
                  nameId, placeholder, type, prefill, conditionalPrefills
  _checkboxes     one entry per choice collected per repetition, each with a
                  fieldName, selectionType ("single" picks one), and options
  _itemOrder      what puts the two lists back in one order, each entry naming
                  the array its own type lives in

Generated field names come out as <nameId>_<n>, so entry 2's Make is `Make_2`.
Those are the names field_config must map to the PDF's slot-2 field.

A COLUMN THAT IS A CHOICE

Rows often end in a choice rather than a box - "lives with you? yes / no", "my
number / a child's number". Write it in the hints as a field with options, and
the compiler builds the checkbox side of the block:

    { "label": "Lives with you?",
      "selection": "single",
      "options": [
        { "label": "Yes", "nameId": "{n}_lives_with_you_yes" },
        { "label": "No",  "nameId": "{n}_lives_with_you_no" } ] }

"single" renders the options as one exclusive choice per entry. The PDF still
gets a box per option: the runtime mirrors the chosen radio into a hidden
checkbox named for the field it fills, and switching the answer removes the old
mirror, so exactly one box is ever ticked in a row.

WHERE THE NUMBER SITS

{n} goes wherever the PDF put the number, and the block absorbs whatever its
hints name - it does not match a pattern on the family prefix. Firearms number
the entry ({n}_description -> firearm_item_2_description); a special finding on
a debt numbers the field (special_finding_debt_{n} ->
property_debt_special_finding_debt_2). Both are one rule.

NUMBERED IS NOT ALWAYS REPEATED

"Which of the debts resulted from the abuse? (check all that apply)" prints one
box per debt and is ONE multi-select question whose options happen to be
numbered. A family every one of whose fields hangs off the same question is
already asked once, and needs no block.

HOW TO CHECK

Group every question nameId matching `<base>_<number>_<field>`. Any base with
more than one number is a repeated block that should be one node:

    node -e '
    const p=require("./dv-packet-project.json");
    const g={};
    for (const f of p.forms) for (const c of f.flowchart.cells) {
      if (!(c.style||"").includes("nodeType=question")) continue;
      const m=(c._nameId||"").match(/^(.*?)_(\d+)_/);
      if (m) (g[m[1]]=g[m[1]]||new Set()).add(m[2]);
    }
    Object.entries(g).filter(([,s])=>s.size>1)
      .forEach(([k,s])=>console.log(s.size, k));
    '

Note the min. Use 0 where the block is genuinely optional, so a user with no
animals is asked once and moves on. Use 1 where the PDF requires at least one.

NAME AND NUMBER THE ENTRIES

entryTitle names one entry, and the generated form appends the number:

    entryTitle "Restraining Order"  ->  Restraining Order #1
                                        Restraining Order #2

Two boxes headed "Order" and "Order" give a person no way to say which one they
are filling, and no way to check what they typed against the numbered rows on
the printed form. Name the thing, singular, as it reads on the form: "Restraining
Order", "Firearm or Ammunition", "Protected Person" - not "Item", "Entry" or
"Order".


================================================================================
RULE 4 — THE MAXIMUM PATH FILLS THE RIGHT FIELDS
================================================================================

Run the debug menu's "Fill maximum path" (Ctrl+Shift in the preview), complete
the form, and produce the PDFs. Two things must hold, and they are not the same
thing.

4a. THE FIELDS FILL

  Every field the answers reached carries a value. A field left blank must be
  blank because the answers ruled it out — the gender is Nonbinary so the male
  and female boxes stay clear, the order was Granted so Not-Requested stays
  clear — and not because nothing was wired to it.

  Check by name: every field name in the sanitized PDF should appear as a key in
  what the form posts. What is left over is your Rule 1 violation list.

  For a packet, one PDF per activated form must come out, not just the first.

4b. THE VALUES LAND IN THE RIGHT BOXES

  This is the one that gets skipped, because 4a looks like proof and is not.

  Matching names prove a value went *somewhere*. They say nothing about whether
  height went into the height box or the weight box, or whether the restrained
  person's address landed in the protected person's block. A swapped pair scores
  100% on 4a and is completely wrong on the filed form.

  The check is visual and there is no shortcut:

    1. Fill each field with a value that identifies it — make
       `person_to_restrain_age` print the literal text
       `person_to_restrain_age`, not "Test Value".
    2. Render every page of the filled PDF.
    3. Read each page against the blank form and confirm each marker sits in the
       box named after it.

  "Fill maximum path" is a coverage tool. It proves fields CAN be filled. It
  cannot tell you they were filled correctly, and a green result from it is not
  evidence for 4b.

BEYOND THE MAXIMUM PATH

The widest path is one path. Before shipping also run:

  - the minimum path — the "Fill minimum path" button, every gate answered the
    way that opens the least. Check the blocks behind those gates disappeared.
  - a typical path — what a real filer would actually enter
  - each branch that switches another form on or off; for the DV packet that is
    DV-110 both served and not served
  - realistic data — long text that overflows a fixed-width box, real dates,
    apostrophes in names. "Test Value" overflows nothing and reveals nothing.


================================================================================
RULE 5 — EVERY FORM HAS EXACTLY ONE GROUP, NAMED AFTER THE FORM
================================================================================

All forms will have exactly one group configured, and that group is the form
name itself. One form, one group, named DV-100 / DV-109 / DV-110 — never two
groups in a form, never a group called "Group 1".

The group is what the progress bar counts. A packet of three forms should read

    1 DV-100    2 DV-109    3 DV-110

and tell a filer how much of the packet is left. Without groups the stepper
falls back to one step per section, so the same packet reads as twenty steps
named "Parties", "Abuse", "Other Orders" and so on — accurate, useless, and it
hides the form boundary that actually matters.

HOW TO CHECK

  1. In the exported GUI JSON, read `groups`.
  2. One entry per form, in form order, each named after its form.
  3. Each entry's `sections` lists that form's sections and nothing else.
  4. No section name appears in two forms. Groups match sections by their
     display name, so a name used twice can only ever belong to one group.

The project export warns on the console about both failure modes: groups that
hold no sections, and section names shared between forms.

WHAT YOU NO LONGER HAVE TO DO

A form whose single group lists no sections gets that form's sections
automatically at export. Naming the group is enough. What is still on you is the
name itself, and the one-group-per-form shape: two empty groups in one form say
nothing about where the split falls, so the export leaves both empty and the
packet drops back to section steps.


================================================================================
RULE 6 — ASK ONLY WHAT THE FILER COMPLETES
================================================================================

Every Judicial Council form prints who completes it, and the packet must obey it.

  DV-100   the request. The filer completes all of it.
  DV-109   "The person asking for a restraining order must complete items 1 and
           2. The court will complete the rest of this form."
  DV-110   the same, for items 1, 2 and 3.

A field the court completes is marked `"courtUse": true` in the field config. It
stays on the PDF, blank, and never becomes a question.

WHY THIS IS NOT COSMETIC

Before this rule the packet asked a survivor "What did the judge decide about
the Stay-Away Order?", "What is the clerk certificate date?", and "Serve DV-110
with this notice?" - 139 questions no filer can answer. Answering them at all
produces a filed order that says the court ruled something it has not. The
interview was two thirds longer and every extra question was wrong to ask.

HOW TO CHECK

  node pipeline-audit.js

reports, per form, how many filer fields are reachable and how many are left for
the court. It fails on a question, in THIS form's own sections, that fills a
court field. A court field filled by an answer an earlier form already collected
is reported separately and is fine - DV-110 item 2 says in print "Include
information from form DV-100, item 9".

WHAT IS STILL ASKED

After the rule, DV-109 asks nothing of its own: both party names and the court
came from DV-100, so its sections collapse and the packet drops the empty step.
DV-110 asks ten questions - the physical description of the restrained person
that police need to enforce the order, which appears on no other form.


================================================================================
RULE 7 — A FORM THAT ASKS NOTHING STILL SHIPS
================================================================================

In a packet, a form can legitimately have no questions of its own, and that is a
result to check rather than a bug to fix.

DV-109 has exactly four fields the filer completes: the court's name and
address, the case number, "Person Asking for Protection" and "Person to Be
Restrained". Every one of those is an answer DV-100 already collects.
dv-packet-connections.json renames them to DV-100's field names, the packet
collapses the duplicates, DV-109's section ends up with zero questions - and the
export drops it, because a step with nothing in it is a page the filer clicks
Next through twice for a form they never fill.

So the packet's progress bar reads DV-100, DV-110. There is no DV-109 step, and
there should not be.

WHAT MUST STILL BE TRUE

The form is still produced and still filled. A form that asks nothing is not a
form that was dropped:

  - it stays in projectForms with its own pdfFile, and its activation still
    decides whether it is produced
  - Download PDFs produces it
  - Preview PDFs lists it, so the filer can read it before filing
  - its fields carry the answers that came from the earlier form

HOW TO CHECK

  node pipeline-fill.js --render

and read that form's PDF. DV-109 on the last run:

    6/17 text fields filled - court name, case number, both party names
    11 blank - every one a court field: hearing date, department, room, the
    judge's rulings, the clerk's certificate

If the form comes back empty, the connections did not apply and the answers
never reached it. If it does not come back at all, it was dropped rather than
collapsed.

WHAT FAILURE LOOKS LIKE

Quiet. The interview looks shorter and cleaner, the filer never sees the form,
and nothing says whether it was filled or forgotten. This is exactly how a
missing PDF hides: Preview PDFs used to list the first form only, so DV-109 and
DV-110 were about to be filed with no way to look at them first.


================================================================================
RULE 8 — ONE QUESTION ASKS ONE THING
================================================================================

"What is the court's name and street address?" is two questions:

    What is the name of the court?
    What is the court's street address?

A person answers one thing at a time. A box asking for two makes them decide the
format - one line or two? a comma? - and a filer who gives only the name has
answered the question and still left the form incomplete. This is not about
wording: no rephrasing of a two-part question makes it one question.

THE PDF KEEPS ITS FIELD

The PDF is not ours to change: DV-100 prints one box, and its AcroForm field is
called court_name_and_street_address. So the interview splits and the pipeline
rejoins - the two answers are concatenated into the field the PDF expects:

    "splits": [
      { "field": "court_name_and_street_address",
        "join": ", ",
        "parts": [
          { "nameId": "court_name",           "question": "What is the name of the court?" },
          { "nameId": "court_street_address", "question": "What is the court's street address?" }
        ] } ]

The compiler replaces the field with its parts and emits a linked-logic node
holding the separator; the generated form keeps a hidden field of the original
name whose value is the parts joined in order, and that is what /edit_pdf fills.
Nothing in that path knows what a court is - any field can be split, with any
separator, on any form.

Two things a split has to respect:

  - A part's name may collide with a field the generated form makes for itself
    (form_zip, current_date, court_name, court_address and the rest). The
    question's name wins and the built-in is not emitted; before that, two
    elements shared an id, getElementById returned the empty built-in, and the
    answer never reached the PDF.
  - Split parts are not mirrors. Mirror housekeeping clears the shorter of two
    boxes holding "the same" value, which on a join deletes the court's name
    because the street address is longer.

HOW TO CHECK

  node pipeline-audit.js

fails on a value question whose field name joins two nouns (X_and_Y) with no
split declared. It also lists questions whose wording contains "and" for a human
to read: "names of people who heard or saw what happened" is one answer despite
the conjunction, and a rule that failed on wording alone would be wrong more
often than right.


================================================================================
RULE 9 — FIELDS ABOUT ONE SUBJECT ARE ONE QUESTION
================================================================================

An address is one thing a person types in one go:

    What is your street address?     ->   Where can the court send you papers?
    What is your city?                      Street address  [            ]
    What is your state?                     City            [            ]
    What is your ZIP Code?                  State           [ dropdown   ]
                                            ZIP code        [            ]

Four screens for one address is four chances to abandon the form, and it hides
the shape of what is being asked. The same is true of any run of fields that
describe one subject - a lawyer's name, bar number and firm; a phone, fax and
email.

This is the opposite of rule 8 and does not contradict it: rule 8 is about one
BOX holding two answers, this is about one ANSWER split over several questions.
Both end at the same place - the interview matches how a person thinks, and the
PDF gets exactly the field values it had before.

HOW IT IS BUILT

A combines hint names the fields and what to call the question:

    "combines": [
      { "question": "Where can the court send you papers?",
        "fields": [
          { "field": "person_asking_protection_mailing_address",  "label": "Street address" },
          { "field": "person_asking_protection_mailing_city",     "label": "City" },
          { "field": "person_asking_protection_mailing_state",    "label": "State" },
          { "field": "person_asking_protection_mailing_zip_code", "label": "ZIP code" } ] } ]

The compiler emits a multipleTextboxes question whose nameId is the family's
shared prefix, with one box per field named by what is left. The exporter
composes each box's id as <question nameId>_<box nameId>, so the ids are exactly
the PDF field names the separate questions filled. A box labelled State renders
as a state dropdown, and Street/City/State/Zip get address formatting, for free.

HOW TO CHECK

  node pipeline-audit.js

fails on three or more separate questions whose names share a prefix and read as
an address; it reports other shared-prefix runs for a human to judge, because
"name" and "age" share a prefix and are not one question.


================================================================================
RULE 10 — ASK FOR A VALUE IN THE TYPE IT IS
================================================================================

A date typed into a text box has no picker and no agreed format. A phone number
has no keypad on a phone. An age accepts "Test Value".

    What is your age?             number   ->  digits only
    What is your date of birth?   date     ->  a date picker, one format
    What is your telephone?       phone    ->  (555) 555-5555 as you type
    What is your email address?   email    ->  the address keyboard, and a check

Set it in the hints, on the field or on a box inside a combined or repeating
question:

    "questions": { "person_to_restrain_date_of_birth": { "type": "date" } }
    "repeats":   [ { "fields": [ { "nameId": "{n}_due_date", "type": "date" } ] } ]

THE NUMBER TYPE IS CALLED "money" INSIDE THE BUILDER

Worth knowing before chasing a bug that is not there: the builder's type list
reads <option value="money">Number</option>, and "currency" is the type for
money. So a number question is exported with type "money" - that rename in
library.js is what makes it render at all, and removing it emits a type the
builder cannot hold, which renders as a bare label with no input.

The control itself steps in whole numbers and prompts "Enter a number". It used
to step in hundredths and prompt "Enter amount", which is what asked a filer's
age, and a distance in yards, in an amount box.

WHAT THIS COSTS IF IGNORED

The PDF still fills - a text box will happily post "2024-06-15" - so nothing in
the audit trail looks wrong. What breaks is the person: a filer typing a date
their own way, a phone number the court cannot dial, and no keyboard help on the
device most of them are using.

HOW TO CHECK

  node pipeline-audit.js

fails on a value question whose name says date, phone, email, age, count, years,
months or yards and whose type is still text - inside combined and repeating
questions as well as on its own.


================================================================================
RULE 11 — A QUESTION SAYS WHAT TO ENTER
================================================================================

"What is your custody case details?" is answerable only by someone holding the
paper form - which is the person the interview exists to spare. The form says
what it wants:

    "(If you know, list where the case was filed (city, state, or tribe), the
     year it was filed, and case number.)"

So ask for those three things by name, in one question, with a box each:

    What do you know about the custody case?
      Where it was filed (city, state, or tribe)  [            ]
      Year it was filed                           [            ]
      Case number                                 [            ]

A catch-all noun - details, information, info - in a single free-text box is the
tell. The parenthetical under the field almost always lists the parts; if it
does not, the field is genuinely one value and the question should name that
value ("What is the case number?"), not ask for "details".

THE PDF STILL GETS ONE VALUE

The PDF prints one box, so the parts rejoin exactly as rule 8 describes - split
the field, then combine the parts back into one question:

    "splits": [
      { "field": "other_court_case_custody_details", "join": ", ",
        "parts": [
          { "nameId": "other_court_case_custody_details_location",
            "label": "Where it was filed (city, state, or tribe)" },
          { "nameId": "other_court_case_custody_details_year",
            "label": "Year it was filed" },
          { "nameId": "other_court_case_custody_details_number",
            "label": "Case number" } ] } ],
    "combines": [
      { "question": "What do you know about the custody case?",
        "conditional": { "onlyWhen": "other_court_case_custody_selected" },
        "fields": [ ...those three part names... ] } ]

Name every part with the original field as its prefix. The combine takes the
shared prefix as its nameId and the exporter composes each box id as
<question nameId>_<box nameId>, so the ids come back to exactly the part names
the join is waiting for. Get the prefix wrong and the boxes fill nothing,
silently.

A split's parts inherit no gate. If the original field was conditional, the
conditional has to be restated on the combine - deleting the old question hint
takes its gate with it, and all six court-case questions started showing for
every kind of case.

HOW TO CHECK

  node pipeline-audit.js

fails on a single-box question whose wording contains details, information or
info. It cannot see a question that is vague without using one of those words,
so read the list once per form.

================================================================================
RULE 12 — A NARRATIVE BOX IS ASKED AS A NARRATIVE
================================================================================

Where the form rules eight lines and prints its own instructions, it wants a
story, and the interview has to ask for one. DV-100 item 5f:

    "Give more details about how the person in 2 was abusive on this day.
     Details can include what was said, done, or sent to you (examples: text
     messages, emails, or pictures), how often something happened, etc."

Asked as "What happened?" in a one-line text box, that produces a sentence
where the judge needs a paragraph, and it throws away every prompt the form
gives about what to include. Ask it with a bigParagraph node and carry the
guidance into the question:

    "Describe how the person was abusive that day, including what they said,
     did, or sent to you, and how often it happened."

    "questions": {
      "most_recent_abuse_details": {
        "type": "bigParagraph",
        "text": "Describe how the person was abusive that day, including ..."
      } }

WHAT COUNTS AS ONE

The PDF says so itself: a text widget with the multiline flag set is a box the
form drew several ruled lines for. That is the whole test - no guessing from
wording, no judging by field name. DV-100 has 17 such boxes, DV-109 three,
DV-110 five; most of DV-109's and DV-110's are court fields and are never asked.

Two exceptions:
  - a court field is not asked at all (rule 6)
  - a split's parts share the original's tall box but are each one short value,
    so court_name_and_street_address does not qualify

WORDING, NOT JUST TYPE

Changing the type alone leaves "What happened?" on a bigger box. The rule is
both: the right control AND the form's own guidance in the question, because
the person filling it in cannot see the paper form's parenthetical. This is the
same failure rule 11 catches from the other side - there the question named no
parts, here it names no substance.

HOW TO CHECK

  node pipeline-audit.js

fails on any multi-line PDF box whose question is not a bigParagraph. It found
one the day it was written: DV-110's prohibited-items box, asked as a one-liner.
